# Speed proof, plan 1 (phase 0 gate)

Measured on 2026-11-13 against the release build of `dev` at `2b0d602` (the gate's two
fixes included). Every number below is from this machine, under the load it had at the
time. Where a target is missed, the cause and what was tried are given. Nothing is rounded
in the app's favour.

**Result: the gate is not passed.** Launch to first screen is met for the 20k repository
but not for the 100k one. Scrolling has no blank rows, but its p95 frame time in the shipped
engine (WKWebView) is 19–20 ms against a target of ≤ 17 ms. Memory is under 150 MB with r20k
open and idle, but not after scrolling through it.

## Machine and conditions

- Apple M1 Pro (8 cores), 16 GB, macOS 27.2, built-in 120 Hz display. git 2.54.0 (Apple Git-157).
- **The machine was busy throughout.** Unrelated processes (Spotlight, media analysis, browsers,
  other agents) kept the 1-minute load average between **4.6 and 30**, mostly 7–17. Each run's
  load average is recorded in the raw output. Launch times move by several hundred ms from run to
  run under this load (for example 674 → 1618 ms in one r20k series), so treat single launches as
  noisy. The medians are more trustworthy than the maxima, but a quiet machine would very likely
  measure lower.
- The screen locked at about 15:10, and launches after that never painted (see "Not measured").
  Every number here was taken before then.
- Repositories come from `scripts/gen-synthetic-repo.sh`, which is deterministic:
  - **r20k**: 20,000 commits, 200 branches, 494 merges, 27 tags, 102 remote-tracking refs, 10 MB.
  - **r100k**: 100,000 commits, 400 branches, 2,494 merges, 133 tags, 202 remote-tracking refs, 44 MB.
  - Both have 12–20 feature branches in flight at once, 8 authors and subjects of 3–110 characters.
  - Neither has a commit-graph file (see the r100k launch below).

## Method per row

- **Launch.** `scripts/perf.sh <repo>` launches `GitGraph.app` with
  `open -n -a GitGraph.app --env GG_OPEN=<repo> --env GG_PERF_LOG=<file>`.
  - "Spawn" is the wall clock, in unix ms, taken just before `open`. It therefore includes
    LaunchServices, which a Dock click also goes through.
  - The UI marks `first-rows` from the animation frame in which the first real rows are drawn,
    and `fully-loaded` when a snapshot with `loading: false` is shown. The app appends
    `name<TAB>ms since navigation start<TAB>unix ms` for each mark.
  - The table gives `unix ms − spawn`.
  - The app's config folder is moved aside for the run, so no saved session adds tabs. The
    launch path and the session's tabs take the same path at start, since the core pre-opens
    both.
  - **Deviation from the brief:** the brief said to exec the binary inside the bundle directly.
    On this macOS a window started that way is not brought forward. WKWebView gives a window
    hidden behind others no animation frames, so `first-rows` sometimes never came (observed).
    `open --env` passes the variables and activates the window as a user's launch does.
- **Fully loaded.** In the app this is the `fully-loaded` mark as above. In the core, it is
  `crates/gg-core/tests/perf.rs`: timestamps of the `repo-changed` events from a fresh
  `RepoManager`, measured from just before `open`.
- **Scrolling.**
  - `src/lib/perf/scrollProbe.ts`, after the repository is fully loaded:
    1. scrolls the graph from top to bottom in 200 equal steps over 6 s, setting `scrollTop`
       on a timer;
    2. records every `requestAnimationFrame` delta meanwhile;
    3. waits 300 ms;
    4. counts the visible rows that are still skeletons.
  - The graph's probe adds the longest time a visible row stayed a skeleton and the number of
    frames with a skeleton older than 150 ms.
  - **WKWebView** (the shipped engine): `scripts/perf.sh --scroll` starts the app with
    `GG_PERF_SCROLL=1`. The app then injects the probe, runs the scroll and logs the results
    as `scroll-*` perf marks. 6 runs per repository; the table gives medians of runs 2–6.
  - **Control:** `--still` (`GG_PERF_SCROLL=still`) records frames for the same 6 s without
    scrolling.
  - **Chromium:**
    `GG_PERF=1 pnpm e2e e2e/perf --headed --repeat-each=5` runs the same probe on r100k
    against a release `gg-devserver`.
    - Headless Chromium gave a perfectly regular 16.7 ms for every frame, because its frames
      are not driven by a display. That is unrepresentative, so the table uses the headed run,
      which ran at the display's 120 Hz.
  - Caveat: WKWebView caps animation frames at 60 Hz and reports `performance.now()` in whole
    milliseconds, so a flawless 60 Hz stream reads as deltas of 16 and 17 ms. That is why the
    control's p95 is 18 ms and its p50 is 17 ms. "Frames over 25 ms" (half a frame or more
    late) counts dropped frames.
- **Idle CPU.** `perf.sh` waits 20 s after `fully-loaded` with the window open and untouched.
  It then reads the cumulative CPU time (`ps -o time`) of the app and its WebKit helpers, and
  reads it again 10 s later. The figure is the difference over the wall time: an exact
  average, at 0.1 % resolution.
- **Memory.**
  - The figure is the physical footprint (`footprint -p`) of the app plus its WebKit helpers,
    summed. RSS is listed too.
  - The helpers (`com.apple.WebKit.WebContent`, `.Networking` and `.GPU`) are XPC services
    whose parent is launchd. The script matches them by "responsible process", the attribution
    Activity Monitor uses. It reads that through the unprivileged libsystem call
    `responsibility_get_pid_responsible_for_pid`, via Python ctypes.
  - That call is undocumented. Every run found exactly one helper of each kind for the app.
  - An earlier attempt matched helpers by "new since launch". It picked up three processes of
    another app (Affinity) that started at the same moment, which is why it was dropped.
- **Bundle.** `du -sh` of `target/release/bundle/macos/GitGraph.app` built by
  `pnpm tauri build --bundles app`.

## Misses: cause and what was tried

### Launch to first screen, r100k (median 1.5 s)

**Cause:** git itself.
- The graph needs `git log --date-order`. Without a commit-graph file, git walks the whole
  history before it prints the first commit.
- Time to first byte, measured with git alone: **514–814 ms** on r100k, against 114–119 ms on
  r20k. Everything else in the launch is the same as for r20k (~600 ms).

**With a commit-graph file:** on a copy of r100k after `git commit-graph write --reachable`
(5.7 MB), git's time to first byte fell to **94–111 ms**.
- This file is what `git gc` and `git maintenance` write by default, so many real repositories
  have one.
- The app's launch on that copy was not measured, because the screen had locked.

**Tried:** the two fixes below. They take ~200 ms off every launch, r100k included.

**Not tried, because each needs a decision above this task:**
- have the app write a commit-graph into the user's repository, which changes `.git`;
- show a provisional first screen before the date-ordered walk finishes, which changes the
  layout contract.

### Scrolling p95 in WKWebView (19–20 ms against ≤ 17 ms)

**What the measurements show:**
- No blank rows, ever: 0 rows still skeletons 300 ms after stopping, in all 12 runs, and 0 frames
  with a skeleton over 150 ms.
- The frame-time miss is small. About 1 % of frames are dropped while jumping 100–500 rows per
  step: median 3 of ~360 frames over 25 ms, against 0 in the still control. p95 rises from the
  control's 18 ms to 19–20 ms.
- The control shows that this engine's 1 ms timer and its 60 Hz cap put p95 at 18 ms even when
  nothing happens. As written, the target (≤ 17 ms) cannot be met in WKWebView on this machine.
- In headed Chromium the same code scrolls r100k at 120 Hz with p95 9.2 ms and no frame over
  16.7 ms. So the app's own JavaScript per frame (slot updates, page requests, canvas redraw)
  costs well under 8 ms.

**Tried:**
- Profiling WKWebView's web process with Instruments
  (`xctrace record --attach <WebContent pid>`). It is refused for the system XPC service
  ("Cannot find process"), and `--all-processes` needs privileges. WebKit's paint and
  compositing cost could therefore not be attributed. No blind change was made.

### Memory after scrolling (r20k: 661 MB right after, 278 MB 30 s later)

**Cause:** almost all of it is in `com.apple.WebKit.WebContent`. `footprint` on that process
right after a scroll showed:
- "Owned physical footprint (unmapped) (graphics)": 171 MB dirty plus 2,990 MB reclaimable, in
  1,168 regions. These are tile and backing surfaces painted for each of the 200 scroll
  positions. Forty-five seconds later they were down to 49 MB dirty and 171 regions.
- "WebKit Malloc" (the JavaScript heap and DOM): 100–127 MB, against about 70 MB for the whole
  web process before scrolling. Part of this is the row cache: up to 60 pages of 200 rows, with
  each row about 1.3 KB of JSON, mostly the edges of the lanes passing through it.

**Tried:** nothing that changed it.
- Lowering the row cache's 60-page limit would trim the JavaScript heap, but not the graphics
  memory that dominates.
- Bounding the graphics memory would need a different scrolling structure: a fixed-height
  viewport instead of a natively scrolled 520,000 px tall content. That is a design change.

### Core: first 500 rows on a cold first run (341 ms against < 300 ms)

Only the first run after a build fails, with the repository's pack and the git binary not in
the file cache, at load 12.5. The same test gives 164–171 ms on the next five runs. The time is
git's `--date-order` walk (time to first byte 114–119 ms warm) plus opening (refs, status,
worktrees: about 60 ms warm, 215 ms cold).

## Fixes made (each its own commit, numbers in the commit message)

1. **Read the login shell's PATH while the window is created** (`cf2b54a`).
   - **Before:** Tauri builds the window and webview before its setup hook, so the core, and
     with it git detection, started about 250 ms after launch. Detection runs `$SHELL -ilc` to
     read PATH, which takes 200–360 ms with this machine's zsh profile. The UI's first command
     then waited about 80 ms for the core.
   - **After:** the shell runs on a thread from the first line of `run()`. In instrumented
     launches the core is ready at 362–408 ms, before the UI's first command at 527–571 ms.
2. **Open the session's and the launch repositories as soon as the core starts** (`2b0d602`).
   - **Before:** the UI could ask for its repository only after the page had loaded, at about
     540 ms.
   - **After:** `Core::open_startup_repos` starts at about 370 ms, so the log is already loading
     when the UI asks.
   - Instrumented `open` → first-rows went from 766–833 ms to 658–692 ms.
   - `perf.sh` on r20k, warm median / min: before both fixes 895 / 798 ms (load 10–17); after
     fix 1 931 / 713 ms (load 7–11; within noise); after fix 2 705 / 674 ms (load 9–17).

Suspects from the brief that were checked and found not to matter for the targets:

| Suspect | Finding |
|---|---|
| Row page JSON size | 257 KB per 200 rows, 0.30 ms to serialise |
| `rows()` cost | 0.05 ms |
| HashMap growth during load | r100k loads in 0.75 s |
| Event frequency | 2 `repo-changed` events for r20k |
| Canvas redraw with many lanes | Chromium frames stay under 9.4 ms at p99 |

## Not measured, and why

- **Feedback after a click (< 100 ms).** This task built no click-latency instrumentation. The
  e2e suite checks selection and the busy state functionally, not their timing.
- **Refresh after an on-disk change (< 1 s, no scroll jump).** Not timed on r20k/r100k. The e2e
  graph tests check that an external commit shows within 2 s with `scrollTop` unchanged, and
  that the anchor holds when scrolled. They do not measure the latency on a large repository.
- **App launch on r100k with a commit-graph.** Measured with git alone (above). The app runs
  failed because the screen had locked: a locked screen gives WebKit no animation frames, so
  `first-rows` never comes.
- **Two other launches never painted:**
  - one r100k still-control run (also after the lock);
  - one r100k scroll run at 14:46, before the lock, whose `first-rows` came 21 s late and which
    recorded 0 scroll frames.

  The likeliest cause of the 14:46 run is the window being covered while the machine was in use.
  That cause is not confirmed.

## Reproducing

```sh
scripts/gen-synthetic-repo.sh ~/.cache/gitgraph-perf/r20k 20000 200
scripts/gen-synthetic-repo.sh ~/.cache/gitgraph-perf/r100k 100000 400
GG_PERF_R20K=~/.cache/gitgraph-perf/r20k GG_PERF_R100K=~/.cache/gitgraph-perf/r100k \
  cargo test -p gg-core --release --test perf -- --ignored --nocapture
scripts/perf.sh ~/.cache/gitgraph-perf/r20k             # builds, then 6 launches
scripts/perf.sh --no-build ~/.cache/gitgraph-perf/r100k
scripts/perf.sh --no-build --scroll ~/.cache/gitgraph-perf/r20k   # and --still for the control
GG_PERF=1 pnpm e2e e2e/perf --headed --repeat-each=5     # Chromium
```

Keep the screen unlocked and the app's window uncovered while `perf.sh` runs.
