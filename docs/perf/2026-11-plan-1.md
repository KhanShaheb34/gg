# Speed proof, plan 1 (phase 0 gate)

This page records numbers measured on 2026-11-13 against release builds of `dev`.
- The first round was measured at `2b0d602`.
- Fix round 1 was measured at `b4377d7` and later, with the measurement hooks built in
  (`--features perf`).

Every number is from this machine, under the load it had at the time. Where a target is
missed, the cause and what was tried are given. Nothing is rounded in the app's favour.

**Result:** the coordinator ruled on the gate, with three rulings.

| Ruling | What it says |
|---|---|
| **R18** | The launch gate is judged on r20k, which passes. r100k without a commit-graph is accepted, and the app must not write a commit-graph into users' repositories. |
| **R19** | Scrolling in WKWebView is accepted if three conditions hold: p95 within 2 ms of an idle control, at most 1 % of frames over 25 ms, and 0 skeletons 300 ms after stopping. |
| **R20** | Memory after scrolling is a real miss and had to be fixed. That fix is in fix round 1 below. |

## Machine and conditions

- **Machine:** Apple M1 Pro (8 cores), 16 GB, macOS 27.2, built-in 120 Hz display. git 2.54.0
  (Apple Git-157).
- **The machine was busy throughout.**
  - Unrelated processes (Spotlight, media analysis, browsers, other agents) kept the 1-minute
    load average between **4.6 and 30**, mostly 6–17.
  - Each launch's load average is recorded in the raw output.
  - Launch times move by several hundred ms from run to run under this load. For example, one
    r20k series ran from 674 to 1618 ms.
  - Medians are more trustworthy than maxima. A quiet machine would very likely measure lower.
- **The screen locked twice.** Once at about 15:10 in round 1, and again at about 16:16 in fix
  round 1. While it is locked, WebKit draws no frames, so the app's `first-rows` mark never comes
  and nothing can be measured in WKWebView. Every WKWebView number here was taken with the screen
  unlocked. The numbers that could not be taken are listed under "Not measured".
- **Repositories** come from `scripts/gen-synthetic-repo.sh`, which is deterministic:
  - **r20k:** 20,000 commits, 200 branches, 494 merges, 27 tags, 102 remote-tracking refs,
    10 MB.
  - **r100k:** 100,000 commits, 400 branches, 2,494 merges, 133 tags, 202 remote-tracking refs,
    44 MB.
  - Both have 12–20 feature branches in flight at once, 8 authors, and subjects of
    3–110 characters.
  - Neither has a commit-graph file. See the r100k launch below.

## Method per row

- **Launch.**
  - `scripts/perf.sh <repo>` builds the app with `--features perf`, then launches it with
    `open -n -a GitGraph.app --env GG_OPEN=<repo> --env GG_PERF_LOG=<file> --env GG_CONFIG_DIR=<empty folder>`.
  - Each launch gets its own empty config folder, so the user's own app state is never read or
    changed, and no saved session adds tabs.
  - The script refuses to run while any copy of the app (bundle id `dev.gitgraph.desktop`) is
    running.
  - "Spawn" is the wall clock, in unix ms, taken just before `open`. It therefore includes
    LaunchServices, which a Dock click also goes through.
  - The UI marks two events and the app logs `name<TAB>ms since navigation start<TAB>unix ms`
    for each:
    - `first-rows`: the animation frame in which the first real rows are drawn;
    - `fully-loaded`: when a snapshot with `loading: false` is shown.
  - The table gives `unix ms − spawn`.
  - A launch path and a saved session take the same path at start: the core opens both in the
    background before the page asks for them.
  - **Deviation from the brief:** the brief said to run the binary inside the bundle directly.
    On this macOS a window started that way is not brought forward. A window hidden behind
    others gets no animation frames, so `first-rows` sometimes never came. `open --env` passes
    the variables and activates the window, as a user's launch does.
- **Fully loaded.**
  - In the app: the `fully-loaded` mark, as above.
  - In the core: `crates/gg-core/tests/perf.rs`, which records the timestamps of the
    `repo-changed` events from a fresh `RepoManager`, measured from just before `open`.
- **Scrolling.**
  - What the probe does (`src/lib/perf/scrollProbe.ts`), once the repository has fully loaded:
    1. scrolls the graph from top to bottom in 200 equal steps over 6 s, setting `scrollTop`
       on a timer;
    2. records every `requestAnimationFrame` delta meanwhile;
    3. waits 300 ms;
    4. counts the visible rows that are still skeletons.

    The graph also records the longest time a visible row stayed a skeleton, and the number of
    frames that had a skeleton older than 150 ms.
  - **WKWebView** (the shipped engine): `scripts/perf.sh --mixed` alternates launches with
    `GG_PERF_SCROLL=1` (scroll) and `GG_PERF_SCROLL=still` (the control: the same 6 s of frame
    recording without scrolling). The control and the scroll therefore see the same machine
    load.
    - The hook exists only in a `--features perf` build. The probe module is loaded with
      `import()`, so it is not in the app's main chunk.
  - **Reading WKWebView's numbers:**
    - WKWebView caps animation frames at 60 Hz and reports `performance.now()` in whole
      milliseconds. A perfect 60 Hz stream would therefore read as deltas of 16 and 17 ms.
    - So when the idle control's p95 is 18 ms, that is real jitter from the machine's load.
      It is not timer resolution. (Round 1 claimed it was; that was wrong.)
    - "Frames over 25 ms" means half a frame or more late, which counts dropped frames. Both
      the median and the worst launch are reported, as a share of all frames.
  - **Chromium:** `GG_PERF=1 pnpm e2e e2e/perf/scroll.spec.ts --headed --repeat-each=5` runs the
    same probe on r100k against a release `gg-devserver`.
    - Headless Chromium gives a regular 16.7 ms for every frame, because no display drives its
      frames, so it is not representative.
    - Headed Chromium ran at the display's 120 Hz.
- **Click feedback.**
  - **Chromium** (`e2e/perf/interaction.spec.ts`):
    - Playwright makes real mouse clicks on 20 different rows of r20k.
    - The time runs from the `pointerdown` event's timestamp to the first animation frame in
      which the row is selected, which is the frame that paints the selection.
  - **WKWebView** (the probe, after the scroll):
    - The probe dispatches a `click` event on the subject of 20 visible rows.
    - The time runs from just before dispatch to the first frame in which the row is
      selected. This leaves out the operating system's input delivery.
- **Refresh** (`e2e/perf/interaction.spec.ts`, Chromium, release devserver).
  - Setup: a fresh r20k in a temp folder, scrolled to row 10,000.
  - Changes: 5 empty commits and 5 branches moved onto the top visible commit, made with git
    from the test.
  - The time runs from git's exit to the first animation frame that shows the change: the row
    count has grown, or the label is in the DOM.
  - After each change the test checks that the top visible row is the same commit at the same
    offset.
  - WKWebView was not measured for this; see "Not measured".
- **Idle CPU.**
  - `perf.sh` waits 20 s after `fully-loaded` with the window open and untouched.
  - It reads the cumulative CPU time (`ps -o time`) of the app and its WebKit helpers, then
    reads it again 10 s later.
  - The figure is the difference over the wall time: an exact average, at 0.1 % resolution.
- **Memory.**
  - The figure is the physical footprint (`footprint -p`) of the app plus its WebKit helpers,
    summed, and given per process. RSS is listed too.
  - It is taken right after the scroll and again 30 s later. WebKit lets go of its graphics
    surfaces some time after scrolling.
  - The helpers (`com.apple.WebKit.WebContent`, `.Networking` and `.GPU`) are XPC services
    whose parent is launchd.
  - They are matched by "responsible process", the attribution Activity Monitor uses. The
    script reads it with the unprivileged (but undocumented) libsystem call
    `responsibility_get_pid_responsible_for_pid`, via Python ctypes.
  - Every launch found exactly one helper of each kind.
- **Bundle.** `du -sh` of `target/release/bundle/macos/GitGraph.app`, built by
  `pnpm tauri build --bundles app`.

## Fix round 1

### Memory after scrolling (R20)

**Cause found in round 1.** After a top-to-bottom scroll of r20k, the web process held 600+ MB,
most of it graphics memory:
- 171 MB dirty plus 2,990 MB reclaimable, in 1,168 regions;
- 49 MB in 171 regions, 45 s later.

The row pool was positioned inside the scrolled content, which is as tall as the whole history.
So every jump made WebKit paint, and keep, new tiles of that content.

**Fix** (`b4377d7`):
- The rows and the lane canvas now live in one container: the `rowgroup`, the size of the
  rendered rows.
- That container moves with `translateY` on its own layer (`will-change: transform`), and the
  rows inside it are positioned relative to it.
- The history-tall spacer paints nothing. Rows and lanes still move with the scrolled content
  together, so lines never lag behind text.
- `RowCache` now keeps 8 pages instead of 60: the window, 400 rows of prefetch either way, and
  one page on each side.

**Checked by:**
- An e2e test: the `rowgroup` is at most a few viewports tall, holds the canvas, and is its own
  layer, while the scrolled content stays as tall as the history. With the old view it fails at
  78,000 px.
- A unit test: the cache keeps at most 8 pages.
- All graph e2e tests still pass: scroll anchoring, column resize, generation swap and ARIA row
  indices.

### Errors of repositories opened at start

- **The problem.** A repository opened by the core before the page listened (the launch path, or
  a session tab) reported a watcher failure or a failed log load as `repo-error` too early. Nobody
  saw it.
- **The fix.** Such errors are now held, the latest of each kind, until the page's `open_repo`
  adopts the repository, and are then emitted once.
- **Also fixed.** A second open of a repository that is still being opened now waits for the
  first one. Before, it read the repository and created a watcher again. (`a5cc2a1`)

### Measurement hygiene

- The core perf tests run one at a time and assert on the median of three warm opens.
  (`ef40f27`)
- The measurement hooks are only in a `--features perf` build. `perf.sh` uses its own config
  folders and never touches the user's. Clicks are measured. (`c266e98`)
- The login-PATH prefetch test uses a stand-in shell and checks that `detect` waits for it.
  (`850fb3e`)

## Misses: cause and what was tried

### Launch to first screen, r100k (median 1.5 s): accepted by coordinator (R18)

- **Cause:** `git log --date-order` on a repository without a commit-graph file walks the whole
  history before it prints the first commit.
  - Measured with git alone, the time to first byte is **514–814 ms** on r100k and 114–119 ms on
    r20k.
- **With a commit-graph:** on a copy of r100k with one (`git commit-graph write --reachable`,
  5.7 MB), git's time to first byte was **94–111 ms**.
  - `git gc` and `git maintenance` write this file by default.
  - The app must not write it (R18).

### Scrolling p95 in WKWebView: see R19 and "Scrolling after the fix"

- Instruments refuses to attach to WKWebView's web process (`xctrace record --attach` says
  "Cannot find process"), so WebKit's paint and compositing cost could not be attributed.
- In headed Chromium at 120 Hz, the same code scrolls r100k with p95 9.2 ms and no frame over
  16.7 ms.

## Fixes made in round 1 (launch)

1. **Read the login shell's PATH while the window is created** (`cf2b54a`).
   - **Before:** Tauri builds the window and webview before its setup hook. So the core started
     about 250 ms after launch, and git detection runs `$SHELL -ilc` (200–360 ms with this
     machine's profile).
   - **After:** the shell runs on a thread from the first line of `run()`. In instrumented
     launches, the core is ready at 362–408 ms, before the page's first command at 527–571 ms.
2. **Open the session's and the launch repositories as soon as the core starts** (`2b0d602`).
   - Instrumented `open` → first-rows went from 766–833 ms to 658–692 ms.
   - With `perf.sh` on r20k, warm median / min:

     | Build | Warm median / min | Load |
     |---|---|---|
     | Before both fixes | 895 / 798 ms | 10–17 |
     | After fix 1 | 931 / 713 ms (within noise) | 7–11 |
     | After fix 2 | 705 / 674 ms | 9–17 |

**Checked and ruled out:**

| Suspect | Finding |
|---|---|
| Row page JSON size | 257 KB per 200 rows, 0.3 ms to serialise |
| `rows()` | 0.05 ms |
| HashMap growth during the load | r100k loads in 0.75 s |
| Event frequency | 2 `repo-changed` events for r20k |
| Canvas redraw with many lanes | Chromium p99 9.4 ms |

## Not measured, and why

- **Memory and scrolling after the fix (`b4377d7`), in WKWebView.** The screen locked at about
  16:16. While it is locked, WebKit draws no frames: the first launch after the lock never
  marked `first-rows`.
  - A batch (`perf.sh --mixed`, r20k and r100k, with the old layout as a same-day baseline) is
    queued to run when the screen unlocks.
  - Until then these numbers are **not measured**. No estimate is given.
- **Refresh latency in WKWebView.** Measured only in Chromium.
- **App launch on r100k with a commit-graph.** Measured with git alone (above).
- **Launches that never painted:**
  - every launch while the screen was locked;
  - one r100k scroll run at 14:46, before the first lock, whose `first-rows` came 21 s late. The
    window was probably covered; that is not confirmed.

## Reproducing

```sh
scripts/gen-synthetic-repo.sh ~/.cache/gitgraph-perf/r20k 20000 200
scripts/gen-synthetic-repo.sh ~/.cache/gitgraph-perf/r100k 100000 400
GG_PERF_R20K="$HOME/.cache/gitgraph-perf/r20k" GG_PERF_R100K="$HOME/.cache/gitgraph-perf/r100k" \
  cargo test -p gg-core --release --test perf -- --ignored --nocapture
scripts/perf.sh ~/.cache/gitgraph-perf/r20k                    # builds (--features perf), 6 launches
scripts/perf.sh --no-build --mixed ~/.cache/gitgraph-perf/r20k # scroll and still, interleaved
GG_PERF=1 pnpm e2e e2e/perf --headed                           # Chromium: scroll, clicks, refresh
```

Keep the screen unlocked and the app's window uncovered while `perf.sh` runs.
