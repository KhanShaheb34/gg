# Speed and verification, plan 2 (actions)

Measured on 2026-11-14 against release builds of `dev` with the measurement hooks built in
(`pnpm tauri build --bundles app --features perf`), the same way as plan 1
([2026-11-plan-1.md](2026-11-plan-1.md)): `scripts/perf.sh`, its own empty config folder per
launch (`GG_CONFIG_DIR`; the user's own app state is never read or written), launches through
LaunchServices (`open -n -a … --env`), the first launch of each series left out, and any
launch whose window did not paint left out (no `first-rows` mark from an animation frame, or a
probe that did not record its frames and clicks). Every number below is from launches whose
window painted; none had to be left out beyond the first of each series unless a row says so.

**Machine:** Apple M1 Pro (8 cores), 16 GB, macOS 27.2, built-in display; git 2.54.0. The
machine was in use (load average 3–57 at times; each launch's load is in the raw output, kept
in the session scratchpad). The screen stayed unlocked throughout.

**Builds.** The launch, scroll, memory, idle and action numbers are from a `--features perf`
build of `d0b952c`'s tree (Task 11, after the R36, selection, log and core fixes, before the
later UI fixes listed under "Fixed after the measurements"). The real-app walk ran on later
builds, the last at `HEAD` of this task.

## Idle CPU on the large working tree (plan 1's open item)

**Plan 2:** `perf.sh --no-build --runs 6 r20k-tree`: idle CPU **0.00 % (0.00–0.20)**, n=5,
footprint 156.0 MB (149.8–157.4), first rows 710 ms (681–750). Plan 1: 0.69 % (0.10–23.76),
152.3 MB (143.7–332.0), 694 ms.

**Looked for further** (a script in the session scratchpad, `idle.sh`: per process, CPU over
six 10 s windows from 5 s after fully loaded, with the count of new generations shown and
git children running, and `sample` of the busiest process when a window is over 3 %):

- 5 launches untouched, 30 windows: never over 0.4 % in any window (app ≤ 0.3 %, WebContent
  ≤ 0.1 %, GPU 0.0 %), no new generation, no git child. Every window painted (first-rows) and
  the app was frontmost.
- 2 launches with the window losing and regaining focus 3 times in every other window: those
  windows read 3.0–3.3 % (app 1.6–1.8, GPU 0.5–0.6, WebContent 0.6–1.0), the others 0.0–0.2 %.
  **One away-and-back costs about 0.1 s of CPU** in all (the status re-read on focus and the
  window redrawing as active/inactive); no new generation came of it (nothing changed).

**Ruled out:** a scheduled fetch (the first comes one interval after open; r20k-tree's
`origin` is itself); a watcher loop (git runs with `GIT_OPTIONAL_LOCKS=0`, so `git status`
never rewrites the index; no new generation in any window); timers and animations in the page
(the only endless CSS animations are the fetch/refresh spinners, the loading line and the busy
pill's spinner, shown only while those run; none ran); Plan 2's additions — the busy
indicator's 150 ms timer runs only while an operation runs, notice timers only while a notice
is up, the banner looks again only on pointer or focus entering it (at most once a second),
and the closed command log asks nothing (e2e: 0 `command_log` requests in 3 s with changes
coming in). Focus changes cost ~0.1 s each; 23.8 % would need ~24 a second.

**Not found:** what made plan 1's single 23.8 % launch (WebContent at 237 MB, as if it drew
continuously). It did not happen again in 12 launches (5 + 5 + 2) of r20k-tree here. Recorded
as not reproduced; no fix made for it.

## Fixed after the measurements (from using the app)

Found while using the real app and the screenshots, fixed with tests, after the builds
measured above (the measurements were not repeated; none of these touches scrolling or
loading):

- A right-click, click or double-click acts on the commit and label its row shows, checked
  by the row's drawn hash and the label's name, not what the row cache holds at that index
  (in the walk, "Check out" on `main`'s label checked out another branch).
- Checking out a branch deleted in a terminal meanwhile fails plainly (`--no-guess`) instead
  of git recreating it from `origin/<name>`.
- A menu no longer closes when the app scrolls by itself (the graph keeping a row in view as a
  panel opens late; the command log following new commands); the wheel and clicks still close
  it.
- The panels follow the banner's size in the next frame: a "ResizeObserver loop" error that
  appeared when the banner came up over the details and the log is gone (it counted as a page
  error in the walk).
- Cmd+W pressed again while a tab is still closing closes the next tab.
- Notices the UI writes end with a full stop; a copied hash says "Copied the hash.".

## The real app, used (WKWebView, release build with hooks)

`GG_PERF_SCROLL=walk` (`src/lib/perf/walkProbe.ts`) uses the real window the way a person
would: DOM events on the real menus, dialogs, notices, banner and log, in WKWebView, with the
real core and git. Its driver (`walk.sh`, session scratchpad) makes a throwaway repository with
a bare `origin` beside it and a second clone that pushed to it (`staging` 2 behind
`origin/staging`, a `feature/login`, a `remote-only` branch on the remote, `clash` and `topic`
that conflict with `main` on `app.txt`, a tag), launches the app on it with its own config
folder, changes files when the walk asks (a conflict resolved "in an editor", a change to
stash) and screenshots the window at marked points. 23 steps:

| Steps | Seen |
|---|---|
| Staging routine: Check out `staging` → "Fast-forward 2 commits first?" → Yes; Merge `feature/login` into `staging…` → Merge; the notice's "Push staging to origin" | "Checked out staging. It was fast-forwarded to origin/staging."; the merge notice with its Push button; "Pushed staging to origin." |
| Commit menu, each item: Create branch here…, Create tag here…, Copy hash, Copy message, Cherry-pick…, Revert…, Reset → Soft, Reset → Hard (red confirmation), Check out this commit | each done, with its notice ("Cherry-picked 1c969456 onto walk/branch.", "Reset walk/branch to d7337900: uncommitted changes were discarded.", …); the hard reset only after the red confirmation |

Runs: 10 walks on builds as fixes went in. The first runs failed on the walk's own selectors
(fixed in the walk, not the app). Then:
- **Found in the app by the walk**, all fixed (see "Fixed after the measurements"): menus closed
  by the app's own scrolling (the reset submenu and the tag menu vanished under the walk); the
  "ResizeObserver loop" page error (4 in one run, 0 after); the wrong-target menu above.
- On the last builds: steps 1–20 passed in one run (`walk7`), steps 1–17 in another (`walk9`);
  step 21 (rebase) passed in `walk4`, 22 (stash) and 23 (log) in `walk5` and `walk8`. Every
  step has passed in the real window at least once; **no single run passed all 23 after the
  last fix**: the two runs after it (`walk9`, `walk10`) stopped when the owner brought another
  app to the front (a covered window gets no animation frames, and the walk waits for frames;
  the menu also closes when the window loses focus). Those runs count as not painted after
  that point and nothing from them is claimed.
- Page errors: 0 in every run after the ResizeObserver fix.

**Seen in the window screenshots** (scratchpad, `walk*/`): menus at the pointer and inside the
window, the fast-forward and merge dialogs, the merge notice with Push, the red confirmations,
the banner over details and the open log (in a small window the graph keeps 160 px and the
rest is shared), the log with the failed operation highlighted. The command log shows a
conflicted merge's `git merge` as a red "exit 1" although the operation stopped (not failed)
— accurate, but alarming; left as is (noted).
