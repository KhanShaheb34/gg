# Speed and verification, plan 3 (worktrees, pull requests, release)

Measured on 2026-11-16 against release builds of `dev` with the measurement hooks built in
(`pnpm tauri build --bundles app --features perf`), the way plans 1 and 2 were
([2026-11-plan-1.md](2026-11-plan-1.md), [2026-11-plan-2.md](2026-11-plan-2.md)):
`scripts/perf.sh`, its own empty config folder per launch (`GG_CONFIG_DIR`), launches through
LaunchServices (`open -n -a … --env`), the first launch of each series left out, and launches
whose window did not paint left out (none had to be, beyond the first of each series).

**Machine:** Apple M1 Pro (8 cores), 16 GB, macOS 27.2, built-in display; git 2.54.0 (Apple
Git-157). The machine was in use throughout (1-minute load 2.8–10.6 in the final series; each
launch's load is in the raw output, kept in the session scratchpad). The repositories are plan
1's (`scripts/gen-synthetic-repo.sh`, cached in `~/.cache/gitgraph-perf/`): r20k (20,000
commits, 200 branches) and r20k-tree (r20k with a 50,000-file working tree). The worktree
timings use local clones of them with linked worktrees added (`git clone --local`, then
`git worktree add`), in the scratchpad.

**Plan 2 side by side.** Load moves launch times by hundreds of milliseconds, so plan 2's
final build (`a683fcf`, the base of plan 3, built the same way from `git archive`) was measured
again here, in series interleaved with plan 3's: plan 2's `scripts/perf.sh`, then plan 3's,
twice for idle (4 launches each) and twice for scrolling (3 launches each). "Plan 2 (again)" is
that build under the same load as "Plan 3"; "Plan 2 (its doc)" is what plan 2 recorded on
2026-11-14 under a quieter load. Plan 3 is the build at `64c1314`.

### Against plan 2: launch slower after navigation, not fixed; memory +6 MB idle and +22 MB after scrolling

**Launch: a miss against plan 2, its cause not found.** Read from the table above, not from
an average over series:

- In the idle series, where the marks after navigation were taken, plan 3 is **154 ms
  behind** plan 2 to fully loaded (840 against 686 ms), and **navigation → first rows is
  431 ms against 158 ms: 2.7 times plan 2's, +273 ms**. All of the gap is after navigation
  start; the time to navigation start is not longer.
- Spawn → first rows over both series is 808 against 750 ms (+58 ms), but the scroll series
  alone shows only 20 ms: the series disagree by as much as the gap, so +58 ms is not a
  measure of it. The spec's target (< 1 s) is met either way.
- What was tried: timing marks in a scratch build (not kept) showed the core waiting for the
  login shell that tells it git's `PATH`, which e579d97 had moved behind the window's
  creation; **64c1314** starts it before the window again (in a plugin set up right after
  single-instance). In that scratch build navigation → first rows then measured 160–300 ms,
  but the final build, measured afterwards in the series above, still shows 431 ms (257–479).
  So 64c1314 did not close the gap as measured, and what remains is **not explained**: the
  earlier note that it is the page's larger JavaScript (348 against 237 KB) and stylesheet
  (82 against 54 KB) was a guess, never measured, and parsing ~110 KB more script does not
  take ~270 ms on this machine.
- What would tell: the perf build now marks the page's own phases (`page-main`,
  `page-mounted`, `state-asked`/`-answered`, `open-asked`/`-answered`, `first-rows`) and when
  the login shell ran (`login-shell-start`/`-done`, wall clock), and `scripts/perf.sh --logs
  DIR --login-shell` keeps every launch's raw log. A run with them was not possible in the
  final fix wave (see "Not measured"); nothing was lazy-loaded, since the bundle was not shown
  to be the cause.

**Memory (not fixed; cause narrowed only to WebKit).** Idle +6 MB and 30 s after scrolling
+22 MB against plan 2's build side by side. The app process is the same (≈ 50–54 MB in both);
all of the difference is WebKit's WebContent process (idle 80–82 against 75–77 MB; after
scrolling 212–220 against 155–205 MB). Plan 1 traced the after-scroll part to what WebKit
keeps from drawing the rows, given back under memory pressure. The plausible contributors here
are the larger stylesheet (style data for every element) and the side panel, now shown by
default at 1280 px (R19); neither was measured apart. Recorded as a miss against plan 2, inside
plan 1's own spread for idle (151–160 MB) but outside it after scrolling.

## Side panel and worktree switch (new)

`perf.sh --no-build --runs 5 --modes worktrees <repo>` (`src/lib/perf/worktreesProbe.ts`):
10 rounds per launch of ⌘B (panel hidden, then shown: from the key to the frame that paints its
rows), then 10 rounds of "Make active" on another worktree's row (from the click to the frame
that paints the switch on the row, its spinner or the active mark, and to the frame where the
core's new snapshot marks it active with no operation running). n = 4 launches × 10, medians
of the launches' values (min–max), load 3.5–8. Built before 64c1314 (that commit changes only
the start).

| Repository | Panel shown, p50 / p95 | Switch feedback, p50 / p95 | Switch done, p50 / p95 | Target |
|---|---|---|---|---|
| r20k clone, 4 worktrees (8 files each) | 22 / 26.5 ms (24–28) | 4.5 / 6 ms (5–6) | 139 / 141 ms (139–156) | feedback < 100 ms: **met** |
| r20k-tree clone, 2 worktrees (50,000 files in the main one) | 20 / 26.5 ms (24–27) | 4 / 5 ms (5–6) | 140 / 321.5 ms (306–339) | **met** |

The switch is done in ~140 ms; with a 50,000-file worktree one switch in ten (switching
to it: its `git status` over 50,000 files) takes ~320 ms. Feedback comes in the next frame
either way. No page errors; no round missed.

## The real app, used (plan 3's walk)

`scripts/walk.sh --mode walk3|walk3-dark [--size 900x560] [--via-gg]`
(`src/lib/perf/worktreeWalkProbe.ts`) uses the real window through DOM events on the real
elements, with the real core, git and `gg` launcher, on a throwaway repository whose `origin`
is a github.com URL that git's `insteadOf` sends to a bare repository beside it, and with a
recording fake `gh` (the app is given a stand-in login shell whose `PATH` holds only it,
`/usr/bin` and `/bin`). The runs below were made that way, with git reading the user's global
config; that this machine has no `url.*` rewrite was checked, but the claim "no network host
is contacted" held only for this machine's config (Task 13 review I1). Since the final fix
wave the scripts make it hold on any machine: git runs without global and system config
(`GIT_CONFIG_GLOBAL` an empty file, `GIT_CONFIG_NOSYSTEM=1`), `origin` has an explicit local
push URL, failing `ssh` and `open` stubs come first on the app's `PATH`, launches are
recorded instead of started, and the perf/walk build is `com.shakirul.gg.perf`, sharing no
WebKit storage, single-instance identity or LaunchServices registration with an installed gg
(Task 13 review I2; earlier runs shared the installed app's identifier).
12 steps: the settings (theme, ISO dates), the staging routine (check out with fast-forward,
merge, push from the notice), the side panel, create a worktree made active, files changed on
disk counted in the panel by themselves (seen 620–680 ms after the driver was asked), commit a
subset, push from the commit notice, create a pull request (its marker then on the worktree),
delete a clean worktree (one plain question), delete one with work (the red confirmation, the
untracked file listed), and `gg` in a terminal into the running app.

| Run | Result |
|---|---|
| 1280×800 light | 12 / 12, 0 page errors |
| 900×560 dark | 12 / 12, 0 page errors |

| 1280×800 light, started by `gg` while the app was not running | 12 / 12; the window painted 606 ms after navigation |

The same probe in the browser build (`GG_WALK=1 pnpm e2e walk`, Chromium against
gg-devserver) passes at both sizes and in both themes.
